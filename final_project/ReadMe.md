## 1. Что мы делали и зачем

### Что нам дали

Нам дали кучу данных о доставках из магазинов — это 34 файла в формате Parquet (это как Excel, только для программистов — хранит данные в сжатом виде). Всего в этих файлах **9.7 миллионов строк** и **25 колонок**.

Проблема в том, что эти данные **денормализованные** — то есть ВСЁ свалено в одну огромную таблицу. Представь себе Excel-таблицу, где в каждой строке повторяется и имя покупателя, и его телефон, и адрес магазина, и данные о каждом товаре. Если человек заказал 5 товаров — его телефон записан 5 раз. Если курьера поменяли — все строки задваиваются.

### Что нас попросили сделать

1. **Нормализовать данные** — это значит разбить одну большую таблицу на несколько маленьких связанных таблиц. Это как вместо одного огромного Excel-файла сделать несколько листов: «Покупатели», «Товары», «Заказы» и т.д., и связать их между собой через ID.

2. **Загрузить в базу данных** через Apache Airflow (это программа-оркестратор, которая умеет запускать задачи по расписанию или по кнопке, следить чтобы они не упали, и перезапускать если что).

3. **Построить 2 витрины** — это готовые таблицы с посчитанными метриками (выручка, средний чек, количество заказов и т.д.), чтобы аналитик мог просто написать `SELECT * FROM витрина` и получить нужные цифры без сложных вычислений.

4. **Упаковать всё в Docker** — чтобы преподаватель мог написать одну команду `docker-compose up --build` и у него всё запустилось. Не надо ничего устанавливать, настраивать — Docker сам скачает всё нужное.

### Какие технологии мы использовали и почему

| Технология | Зачем нужна | Аналогия из жизни |
|------------|-------------|-------------------|
| **Docker** | Упаковывает всё приложение в контейнеры | Как коробка с IKEA — внутри всё что нужно для сборки |
| **PostgreSQL** | База данных, где хранятся таблицы | Как склад с полками — каждая таблица на своей полке |
| **pgAdmin** | Графический интерфейс для PostgreSQL | Как приложение-банк для просмотра счёта — видишь данные через веб-страницу |
| **Apache Airflow** | Запускает ETL-задачи по порядку | Как конвейер на заводе — каждая деталь проходит этапы по порядку |
| **PySpark** | Считает витрины (метрики) | Как калькулятор, но для миллионов строк — обычный pandas не вывезет |
| **Python** | Язык, на котором написаны DAG-и | Основной язык проекта |

## 2. Как запустить у себя на компьютере

### Шаг 0: Установить Docker Desktop

**Что такое Docker?** Это программа, которая создает «виртуальные компьютеры» (контейнеры) внутри вашего компьютера. Каждый контейнер — изолированная среда со своими программами. Нам не нужно устанавливать PostgreSQL, Airflow, Java — Docker сделает это сам.

1. Идём на https://www.docker.com/products/docker-desktop/
2. Скачиваем для своей ОС (Windows/Mac)
3. Устанавливаем (далее-далее-далее)
4. **ВАЖНО:** После установки запускаем Docker Desktop и ждём пока в трее (внизу справа) появится зелёный значок кита
5. Проверяем: открываем терминал (cmd или PowerShell) и пишем:

```bash
docker ps
```

Если видите пустую таблицу с заголовками (CONTAINER ID, IMAGE, ...) — Docker работает.
Если ошибка — Docker Desktop ещё не запустился, подождите минуту.

**ВАЖНО для Windows:** В Docker Desktop зайдите в Settings → Resources → Memory и поставьте **минимум 4 GB** (лучше 6). По умолчанию стоит 2 GB, и контейнеры будут падать.

### Шаг 1: Получить файлы проекта

Если проект в Git-репозитории:
```bash
git clone <ссылка-на-репозиторий>
cd <имя-репозитория>/final_project
```

Если просто папка — скопировать папку `final_project` к себе на компьютер.

### Шаг 2: Запустить всё одной командой

```bash
cd путь/к/папке/final_project
docker-compose up --build
```

**Что происходит после этой команды:**
1. Docker скачивает базовые образы из интернета (PostgreSQL, Airflow, pgAdmin) — **первый раз это 5-10 минут**, потом они кэшируются
2. Собирает наш кастомный образ по Dockerfile (устанавливает Java, PySpark, библиотеки)
3. Запускает 5 контейнеров по очереди
4. PostgreSQL запускается первым, создаёт базу и таблицы
5. Airflow подключается к своей служебной БД, создаёт пользователя admin
6. Всё готово когда в терминале перестают бежать новые строки

**Не закрывайте терминал!** Контейнеры работают пока терминал открыт. Если хотите запустить в фоне — добавьте `-d`:
```bash
docker-compose up --build -d
```

### Шаг 3: Зайти в Airflow и запустить загрузку

1. Открываем браузер: **http://localhost:8080**
2. Логин: **admin**, пароль: **admin**
3. На главной странице видим 2 строки — это наши DAG-и (пайплайны):
   - `etl_load_normalized` — загрузка данных
   - `build_data_marts` — построение витрин

4. **Включаем первый DAG:** кликаем на тумблер слева от `etl_load_normalized` (он станет синим)
5. **Запускаем:** нажимаем кнопку ▶ (Trigger DAG) справа
6. **Ждём ~12-15 минут.** Можно кликнуть на название DAG-а и смотреть прогресс — квадратики будут зеленеть один за одним
7. Когда все 5 квадратиков зелёные — **данные загружены!**

8. Теперь **включаем второй DAG** `build_data_marts` и запускаем его
9. Ждём ~1 минуту — **витрины готовы!**

### Шаг 4: Посмотреть данные в pgAdmin

1. Открываем **http://localhost:5050**
2. Логин: **admin@admin.com**, пароль: **admin**
3. Правой кнопкой на «Servers» → «Register» → «Server...»
4. На вкладке General: Name = `delivery` (любое название)
5. На вкладке Connection:
   - Host: **postgres** (НЕ localhost! Это имя контейнера внутри Docker-сети)
   - Port: **5432**
   - Maintenance database: **delivery**
   - Username: **delivery_user**
   - Password: **delivery_pass**
6. Нажать Save
7. Слева раскрыть: Servers → delivery → Databases → delivery → Schemas → delivery → Tables
8. Правой кнопкой на `mart_orders` → View/Edit Data → All Rows — вуаля, витрина!

### Как остановить всё

```bash
# Просто остановить (данные сохранятся, при следующем запуске не надо заново загружать):
docker-compose stop

# Остановить и УДАЛИТЬ ВСЁ (данные, контейнеры, всё с нуля):
docker-compose down -v

# Запустить снова (если не удаляли):
docker-compose start
```

## 4. Нормализация данных (подробно)

### Что такое нормализация простыми словами

Представь Excel-таблицу:

```
| Заказ | Покупатель | Телефон      | Товар  | Цена | Магазин        | Адрес магазина |
|-------|-----------|--------------|--------|------|----------------|----------------|
| 001   | Иванов    | +7-999-111   | Яблоки | 100  | Сберегайка     | Ленина 10      |
| 001   | Иванов    | +7-999-111   | Молоко | 80   | Сберегайка     | Ленина 10      |
| 001   | Иванов    | +7-999-111   | Хлеб   | 50   | Сберегайка     | Ленина 10      |
| 002   | Петров    | +7-999-222   | Яблоки | 100  | Сберегайка     | Ленина 10      |
```

Видишь проблему? «Иванов» и его телефон записаны 3 раза. «Сберегайка Ленина 10» — 4 раза. Если Иванов сменит телефон — надо обновить 3 строки. А если забыть одну — в базе будет два разных телефона у одного человека. Это называется **аномалия обновления**.

**После нормализации** получается так:

**Таблица «Покупатели»:**
```
| ID | Имя    | Телефон    |
|----|--------|------------|
| 1  | Иванов | +7-999-111 |
| 2  | Петров | +7-999-222 |
```

**Таблица «Магазины»:**
```
| ID | Название   | Адрес     |
|----|------------|-----------|
| 1  | Сберегайка | Ленина 10 |
```

**Таблица «Товары»:**
```
| ID | Название | Цена |
|----|----------|------|
| 1  | Яблоки   | 100  |
| 2  | Молоко   | 80   |
| 3  | Хлеб     | 50   |
```

**Таблица «Заказы»:**
```
| Заказ | Покупатель_ID | Магазин_ID |
|-------|--------------|------------|
| 001   | 1            | 1          |
| 002   | 2            | 1          |
```

**Таблица «Товары в заказе»:**
```
| Заказ | Товар_ID | Количество |
|-------|----------|------------|
| 001   | 1        | 2          |
| 001   | 2        | 1          |
| 001   | 3        | 1          |
| 002   | 1        | 3          |
```

Теперь телефон Иванова хранится **один раз**. Если его надо обновить — меняем одну строку. Адрес магазина тоже хранится один раз. Это и есть нормализация.

### Нормальные формы — что это за «формы»

Это как уровни прокачки. Каждая следующая форма — строже предыдущей.

**1НФ (первая нормальная форма):** Каждая ячейка содержит ОДНО значение (не список, не массив). Например, нельзя записать «Яблоки, Молоко, Хлеб» в одну ячейку — надо отдельные строки. Наши данные уже в 1НФ.

**2НФ (вторая нормальная форма):** Если у таблицы составной ключ (например order_id + item_id), то каждый НЕключевой атрибут должен зависеть от ВСЕГО ключа. Название товара (`item_title`) зависит только от `item_id`, а не от `order_id` — значит его надо вынести в отдельную таблицу `items`.

**3НФ (третья нормальная форма):** Нет транзитивных зависимостей. Что это? Вот цепочка: `order_id → user_id → user_phone`. Телефон зависит от пользователя, а пользователь — от заказа. Значит телефон зависит от заказа **транзитивно** (через посредника). Решение — вынести пользователей в отдельную таблицу.

**Мы выбрали 3НФ** — это стандарт для большинства реляционных баз данных. Не слишком мало (данные всё ещё дублировались бы), не слишком много (BCNF, 4НФ — уже перебор для нашей задачи).

### Наш результат: 7 таблиц

| Таблица | Что хранит | Сколько записей | Первичный ключ | Откуда взялась |
|---------|------------|----------------|----------------|----------------|
| **users** | Покупатели (ID + телефон) | 31 910 | user_id | Убрали user_phone из orders — он зависит от user_id, а не от заказа |
| **stores** | Магазины (ID + адрес) | 3 | store_id | Убрали store_address из orders — он зависит от store_id |
| **drivers** | Курьеры (ID + телефон) | 390 | driver_id | Убрали driver_phone — он зависит от driver_id |
| **items** | Товары (ID + название + категория) | 18 | item_id | Убрали item_title и item_category — они зависят от item_id |
| **orders** | Заказы | 340 000 | order_id | Основная таблица — все атрибуты заказа |
| **order_items** | Какие товары в каком заказе | 4 212 103 | (order_id, item_id) | Связь many-to-many между заказами и товарами |
| **order_drivers** | Какие курьеры назначены на заказ | 340 649 | id (авто) | Для отслеживания СМЕН курьеров — один заказ может иметь несколько курьеров |

**Почему `order_drivers` отдельно?** В данных сказано: «возможны смены курьера». Это значит что на один заказ могут назначить курьера А, потом его снять и назначить курьера Б. Если хранить driver_id прямо в таблице orders — мы можем записать только одного курьера и потеряем информацию о смене. Поэтому отдельная таблица, где может быть несколько строк на один заказ.

**Почему `order_items` отдельно?** В одном заказе может быть 1, 5, 10 товаров. Это классическая связь «многие-ко-многим»: один заказ содержит много товаров, один товар может быть во многих заказах. Для этого всегда делают промежуточную таблицу с составным ключом.

## 5. ETL-процесс (Airflow DAG-и)

### Что такое ETL

**E**xtract — извлечь данные (прочитать Parquet-файлы)
**T**ransform — преобразовать (разбить на таблицы, убрать дубликаты)
**L**oad — загрузить (записать в PostgreSQL)

### Что такое DAG

**DAG** (Directed Acyclic Graph) — направленный ациклический граф. Проще говоря: это набор задач (tasks), связанных стрелочками «что после чего выполнять». Ациклический = нет зацикливания (задача A не может зависеть от задачи B, если B зависит от A).

### DAG 1: `etl_load_normalized` — загрузка данных (~12 минут)

**Файл:** `dags/etl_load_dag.py`

Этот DAG читает 34 Parquet-файла и раскладывает данные по 7 нормализованным таблицам.

**Почему файлы читаются ПО ОДНОМУ, а не все сразу?** Все 34 файла — это 9.7 миллионов строк. Если загрузить всё в оперативную память через `pd.concat()` — процесс упадёт с ошибкой Out of Memory (в контейнере Docker обычно 2-4 ГБ RAM). Поэтому мы читаем по одному файлу, извлекаем нужные данные, пишем в БД, удаляем из памяти и переходим к следующему файлу.

**Задачи DAG-а (в порядке выполнения):**

```
1. truncate_tables (1 сек)
   │  Что делает: Очищает ВСЕ таблицы командой TRUNCATE.
   │  Зачем: Чтобы DAG был ИДЕМПОТЕНТНЫМ — при повторном запуске
   │  результат будет такой же. Не будет дубликатов данных.
   │
   ▼
2. load_dictionaries (13 сек)
   │  Что делает: Проходит по всем 34 файлам, собирает уникальных
   │  пользователей, магазины, курьеров, товары. Загружает в 4 таблицы:
   │  users (31 910), stores (3), drivers (390), items (18).
   │  Почему одной задачей: Справочники маленькие, незачем делить.
   │
   ▼
3. load_orders (84 сек)
   │  Что делает: Проходит по 34 файлам, извлекает уникальные заказы
   │  (340 000 штук). Для каждого заказа берёт строку с заполненным
   │  delivered_at (финальная доставка).
   │  Дедупликация: Один order_id может быть в нескольких файлах
   │  (из-за разных товаров/курьеров) — берём только первую встречу.
   │
   ▼
4a. load_order_items (11 мин)          4b. load_order_drivers (28 сек)
    Что делает: Загружает               Что делает: Загружает пары
    4 212 103 пар (заказ, товар)        (заказ, курьер) — 340 649 записей.
    с ценой, количеством, скидкой.      У снятого курьера delivered_at=NULL.
    Самая долгая задача — много данных.

    ЭТИ ДВЕ ЗАДАЧИ ВЫПОЛНЯЮТСЯ ПАРАЛЛЕЛЬНО (не зависят друг от друга)
```

**Что такое идемпотентность?** Это когда ты можешь запустить DAG 1 раз или 100 раз — результат будет одинаковый. Мы это обеспечиваем через TRUNCATE (очистку) перед загрузкой. Если задача упала на середине — просто перезапускаем весь DAG и всё загрузится правильно.

### DAG 2: `build_data_marts` — построение витрин (~1 минута)

**Файл:** `dags/mart_build_dag.py`

Этот DAG использует **PySpark** (Python-обёртка над Apache Spark) для построения витрин.

**Почему PySpark, а не обычный SQL?**
1. По условию задания: PySpark = **2 балла**, SQL = 1 балл
2. PySpark может обрабатывать терабайты данных (в нашем случае данных меньше, но показываем что умеем)
3. Удобнее писать сложные оконные функции (ранжирование товаров по популярности)

**Как работает Spark с PostgreSQL:**
1. Spark запускается ВНУТРИ контейнера Airflow (мы установили Java + PySpark в Dockerfile)
2. Spark подключается к PostgreSQL через **JDBC** (Java Database Connectivity) — это как мост между Spark и БД
3. Читает таблицы (orders, order_items, и т.д.) в память Spark (DataFrame)
4. Выполняет JOIN-ы, группировки, оконные функции
5. Записывает результат обратно в PostgreSQL (mode=overwrite — перезаписывает витрину)

**Две задачи выполняются параллельно:**
- `build_orders_mart` — считает витрину заказов → `mart_orders` (1 101 строка)
- `build_items_mart` — считает витрину товаров → `mart_items` (19 818 строк)

## 6. Витрины — что мы посчитали

### Что такое витрина

Витрина (**data mart**) — это готовая таблица с агрегированными данными. Аналитику не нужно писать сложные JOIN-ы и GROUP BY — он просто делает:

```sql
SELECT * FROM delivery.mart_orders WHERE city = 'Москва' AND month = 3;
```

И получает все метрики (выручку, средний чек, количество заказов...) для Москвы за март.

### Витрина заказов (`delivery.mart_orders`)

**Гранулярность:** одна строка = один день + один город + один магазин.
**Всего строк:** 1 101 (примерно 1 год × 3 города × ~365 дней, с учетом что данные не за каждый день).

**Разрезы** — это измерения, по которым можно фильтровать и группировать:
- `year`, `month`, `day` — дата
- `city` — город (Москва, Орел, Тула)
- `store_id`, `store_address` — магазин

**Метрики** — что мы посчитали:

| Метрика | Что означает | Как считается |
|---------|-------------|---------------|
| **turnover** (оборот) | На какую сумму ЗАКАЗАЛИ | Для каждого товара: количество × цена. Потом применяем скидку товара (item_discount%) и скидку заказа (order_discount%). Суммируем по всем товарам заказа. |
| **revenue** (выручка) | Какую сумму РЕАЛЬНО получили | Как оборот, но вычитаем отмененные единицы товара (item_canceled_quantity). Если из 10 штук отменили 2 — считаем 8. |
| **profit** (прибыль) | Выручка минус расходы | revenue - delivery_cost (стоимость доставки) |
| **total_orders** | Сколько заказов создали | COUNT DISTINCT order_id |
| **delivered_orders** | Сколько доставили | Заказы, где delivered_at НЕ пустой |
| **canceled_orders** | Сколько отменили | Заказы, где canceled_at НЕ пустой |
| **canceled_after_delivery** | Отмены ПОСЛЕ доставки | И canceled_at, и delivered_at заполнены (заказ доставили, но потом отменили) |
| **canceled_service_errors** | Отмены из-за нас (сервиса) | Причина отмены = «Ошибка приложения» ИЛИ «Проблемы с оплатой» |
| **unique_buyers** | Уникальных покупателей | COUNT DISTINCT user_id |
| **avg_check** | Средний чек | revenue / total_orders |
| **orders_per_buyer** | Заказов на покупателя | total_orders / unique_buyers |
| **revenue_per_buyer** | Выручка на покупателя | revenue / unique_buyers |
| **driver_changes** | Смен курьеров | Считаем заказы, где в order_drivers больше 1 записи (назначали > 1 курьера) |
| **active_drivers** | Активных курьеров | COUNT DISTINCT driver_id (из order_drivers) |

### Витрина товаров (`delivery.mart_items`)

**Гранулярность:** одна строка = один день + город + магазин + товар.
**Всего строк:** 19 818.

**Разрезы:** год, месяц, день, город, магазин, категория, товар.

| Метрика | Что означает | Как считается |
|---------|-------------|---------------|
| **item_turnover** | Оборот товара | количество × цена × (1 - скидка_товара%) × (1 - скидка_заказа%) |
| **ordered_quantity** | Заказано единиц | SUM по item_quantity |
| **canceled_quantity** | Отменено единиц | SUM по item_canceled_quantity |
| **orders_with_item** | В скольких заказах этот товар | COUNT DISTINCT order_id |
| **orders_with_item_cancel** | В скольких заказах отменяли этот товар | Заказы, где item_canceled_quantity > 0 |
| **is_most_popular_day** | Самый популярный за ДЕНЬ | true/false. Считается через оконную функцию RANK() — товар с максимальным quantity за день получает true |
| **is_least_popular_day** | Самый непопулярный за ДЕНЬ | Аналогично, но минимальный |
| **is_most/least_popular_week** | За НЕДЕЛЮ | Аналогично, но группировка по ISO-неделям |
| **is_most/least_popular_month** | За МЕСЯЦ | Аналогично, но группировка по месяцам |

**Как работает определение популярности:** Для каждого дня (или недели/месяца) внутри каждого города и магазина мы ранжируем товары по количеству заказанных единиц. Товар на 1 месте получает `is_most_popular = true`, на последнем — `is_least_popular = true`. Это делается через PySpark-функцию `RANK() OVER (PARTITION BY ..., ORDER BY ordered_quantity DESC)`.

## 7. SQL-запросы для проверки

Эти запросы можно запустить в pgAdmin после загрузки данных:

```sql
-- 1. Проверить что все данные загружены
SELECT 'users' as t, COUNT(*) FROM delivery.users
UNION ALL SELECT 'stores', COUNT(*) FROM delivery.stores
UNION ALL SELECT 'drivers', COUNT(*) FROM delivery.drivers
UNION ALL SELECT 'items', COUNT(*) FROM delivery.items
UNION ALL SELECT 'orders', COUNT(*) FROM delivery.orders
UNION ALL SELECT 'order_items', COUNT(*) FROM delivery.order_items
UNION ALL SELECT 'order_drivers', COUNT(*) FROM delivery.order_drivers
UNION ALL SELECT 'mart_orders', COUNT(*) FROM delivery.mart_orders
UNION ALL SELECT 'mart_items', COUNT(*) FROM delivery.mart_items;

-- 2. Топ-5 дней по выручке
SELECT year, month, day, city, revenue, total_orders
FROM delivery.mart_orders
ORDER BY revenue DESC LIMIT 5;

-- 3. Средний чек по городам
SELECT city, ROUND(AVG(avg_check), 2) as avg_check
FROM delivery.mart_orders
GROUP BY city;

-- 4. Процент отмен по магазинам
SELECT store_address,
       ROUND(SUM(canceled_orders)::numeric / SUM(total_orders) * 100, 1) as cancel_pct
FROM delivery.mart_orders
GROUP BY store_address;

-- 5. Самый популярный товар за каждый месяц
SELECT year, month, city, item_title, ordered_quantity
FROM delivery.mart_items
WHERE is_most_popular_month = true
ORDER BY year, month, city;

-- 6. Топ-3 товара по обороту за всё время
SELECT item_title, category, ROUND(SUM(item_turnover)::numeric, 2) as total
FROM delivery.mart_items
GROUP BY item_title, category
ORDER BY total DESC LIMIT 3;
```

## 9. Частые проблемы и их решения

### «Cannot connect to the Docker daemon»
**Причина:** Docker Desktop не запущен.
**Решение:** Запустить Docker Desktop (иконка кита на рабочем столе) и подождать 30-60 секунд.

### «port is already allocated»
**Причина:** На вашем компьютере уже запущен PostgreSQL (или другая программа) на порту 5432.
**Решение:** Либо остановить свой PostgreSQL, либо в `docker-compose.yml` поменять `"5432:5432"` на `"5433:5432"` (будет доступен на порту 5433).

### «Task exited with return code -9»
**Причина:** Не хватает оперативной памяти в контейнере.
**Решение:** Docker Desktop → Settings → Resources → Memory → поставить 4-6 GB.

### «Airflow не видит DAG-и (пустая страница)»
**Причина:** Airflow сканирует папку dags/ раз в 30 секунд.
**Решение:** Подождать 1-2 минуты и обновить страницу.

### «pgAdmin не подключается к PostgreSQL»
**Причина:** В поле Host написали `localhost`.
**Решение:** Писать `postgres` — это имя контейнера внутри Docker-сети. Контейнеры общаются между собой по именам, а не через localhost.

### «Всё было зеленое, а потом стало красное»
**Причина:** Одна из задач упала (возможно, OOM).
**Решение:** В Airflow кликнуть на красный квадратик → View Log → посмотреть ошибку. Обычно помогает перезапуск: Clear → Confirm.
